# 会員登録からログアウトまでの安全のしくみ

作成日: 2026-09-18

「会員登録する」「ログインする」「サブスクを登録する」「ログアウトする」という一連の流れの中で、
どうやって安全性を保っているかをまとめる。技術的な詳しい仕組みは `src/server/` のコードが正しい情報源で、
ここでは「何を目的に、どういう考え方で作られているか」を、担当しているファイル名や使っている技術の名前とあわせて説明する。
エンジニアとの会話で「ここの話だよね」と指せるように、ファイル名・技術名は正式名称のまま載せている。

## 登場する5つの技術

このアプリは、性質の違う5つの部品を組み合わせて作られている。それぞれ何を担当しているかを、
お店に例えると次のようになる。

| 技術 | お店に例えると | このアプリでの役割 |
|---|---|---|
| **React** | 店頭に立っている看板・受付カウンター | ブラウザに表示される画面そのもの。ログインフォームやサブスクの一覧表示を作っている |
| **Cloudflare** | お店の建物そのもの | サーバー側のプログラムが実際に動いている場所（Workersという実行環境）。世界中にある拠点のうち利用者に近い場所で瞬時に動く |
| **Hono** | 建物の中にいる受付係 | 届いたリクエストを見て「ログインの話か」「サブスクの話か」を仕分け、正しい担当窓口に案内する |
| **Drizzle** | 倉庫の在庫管理をしてくれる係員 | データベースへの指示（保存して・探して・消して）を、人間が読み書きしやすい形で組み立てて伝える |
| **Neon** | 実際にモノを保管している倉庫 | データが物理的に保存されている場所。PostgreSQLという種類のデータベースを、インターネット越しに使えるサービスとして提供している |

以降の説明では、この5つがそれぞれどこで登場するかを具体的に示す。

## 全体の流れとファイルの見取り図

```
[ブラウザ]                       [Cloudflare の建物の中]                     [倉庫]
 React の画面                     Hono が受付、Better Auth/subscriptions.ts が処理    Neon
   │                                    │                                        │
① 会員登録・ログイン画面 ──HTTP──▶ "/api/auth/*" 窓口 ──Drizzle経由──▶ user/session/account の表
   （AuthForm.tsx）                 （create-auth.ts の設定）
   ↓（合鍵＝トークンが返ってくる）
② サブスク一覧・登録画面 ──HTTP──▶ "/api/subscriptions" 窓口 ──Drizzle経由──▶ subscription の表
   （SubscriptionList.tsx）          （まず合鍵を確認 → subscriptions.ts）
   ↓
③ ログアウト操作         ──HTTP──▶ "/api/auth/*" 窓口（合鍵を無効化）
```

`src/server/index.ts` が、ブラウザからの全てのリクエストを最初に受け取る「アプリの玄関」にあたる。
ここで実際に道を仕分けているのが Hono というプログラムで、「ログイン関連の話（`/api/auth/*`）」と
「サブスク関連の話（`/api/subscriptions`）」の2つの入り口に振り分けている。
この玄関自体は Cloudflare の Workers という場所で常に動いている。

## ① 会員登録・ログイン

会員登録・ログイン・ログアウトの実際の処理は、自分たちで一から作っていない。**Better Auth** という、
ログイン機能を専門に作っている外部の部品を組み込んで使っている。この部品にどう動いてほしいかの設定は、
`src/server/auth/create-auth.ts` という1つのファイルにまとまっている。

具体的な流れはこうなる。React で作られたログイン画面（`src/client/AuthForm.tsx`）に入力した内容が、
Cloudflare 上で動いている Hono の "/api/auth/*" という窓口に届く。そこから先は Better Auth が処理を担当し、
データベースへの読み書きが必要なところだけ Drizzle に指示を組み立てさせ、最終的に Neon に保存する。

### パスワードはそのままの形で保存しない

会員登録の際に入力したパスワードは、データベースに読める形では保存されない。Better Auth が専用の変換処理を通して「読んでも元のパスワードが分からない値」に変えてから保存する。

変換後の値は `account` というテーブル（`src/server/db/schema.ts` に定義がある）に入る。この保存命令を実際に組み立てているのが Drizzle で、保存先の倉庫にあたるのが Neon。仮にこの倉庫の中身を誰かが覗き見ることができたとしても、そこからパスワードそのものが分かることはない。

### ログインが成功すると「合鍵」が渡される

メールアドレスとパスワードが一致すると、ログインした証拠として「合鍵」のようなランダムな文字列（トークン）が発行され、ブラウザに預けられる。

この記録は `session` という表（同じく `src/server/db/schema.ts`、保存先はやはり Neon）に1件ずつ積まれる。以降のリクエストにはこの合鍵が自動的に添えられ、サーバー側（Cloudflare上のHono・Better Auth）はこれを見て「誰からのリクエストか」合致を判断する。

合鍵には有効期限があり、期限が切れると自動的に使えなくなり、再ログインが必要になる。

### ログイン画面を偽物からのアクセスから守る

このアプリのログイン処理は、許可した場所（このアプリ自身の画面）から届いたリクエストしか受け付けない。

許可する場所のリストは `create-auth.ts` の中の `trustedOrigins` という項目に書かれている。見覚えのない場所から届いたログインリクエストは、その時点で弾く。

### 会員登録・ログインの画面

ブラウザ側で実際に入力フォームを表示しているのは `src/client/AuthForm.tsx` というファイルで、これは React というライブラリで作られた画面。ここに入力された内容が、上で説明した Cloudflare 上の Hono の "/api/auth/*" という入り口に送られる。

## ② サブスクの登録・閲覧・削除

サブスク関連の入り口は、同じく Hono が受け持つ `src/server/index.ts` の中で `/api/subscriptions` として作られている。

### 合鍵を持たない人は門前払いにする

サブスクの一覧を見る・登録する・削除する、といった操作をする前に、この入り口全体にかけられた「関門」が必ず先に働き、「合鍵を持っているか」を確認する。

この関門は `src/server/index.ts` の中に1回だけ書かれていて、`/api/subscriptions` 配下の全ての操作が漏れなくここを通るようになっている。

合鍵がない、または期限切れの場合は、中身の処理に進む前にその場でアクセスを拒否する。ログインしていない人がサブスクの情報に触れる隙はできない。

### データベースとのやり取りは1つの窓口に絞っている

サブスクの情報を実際に読み書きするプログラムは、アプリ全体の中で `src/server/db/subscriptions.ts` という1つのファイルだけに集約している。一覧を見る・登録する・書き換える・削除する、この4つの操作は全てこのファイルの中の処理を通る。ここでは Drizzle を使って「このユーザーが登録した分だけ」という条件付きの命令を組み立て、Neon に問い合わせている。ここを直接見たり書き換えたりできる場所を1か所に限定することで、後から機能を追加したとき、「うっかりどこかで持ち主の確認を忘れる」が紛れ込みにくい作りにしている。

### 「誰の登録か」を必ずセットで記録する

サブスク情報を1件登録すると、「これは誰が登録したものか」という情報が必ず一緒に記録される。これは `subscriptions.ts` のプログラムがそう書いているだけでなく、**`src/server/db/schema.ts` に定義されている Neon 上の表自体が「持ち主のいないサブスク情報は物理的に作れない」という約束を守っている**。プログラムのどこかにミスがあったとしても、この最後の砦がデータの矛盾を防ぐ。

### 他人のサブスクには触れない

サブスクを更新・削除するときは、`subscriptions.ts` の中で「そのサブスクのIDが一致すること」に加えて「自分が登録した本人であること」の両方が揃わないと処理が実行されないようになっている。これも Drizzle が組み立てる問い合わせの条件に、必ず「登録した本人のIDと一致するか」を含めることで実現している。
他人が登録したサブスクのIDを何らかの方法で知っていたとしても、その操作は失敗する。

さらに、失敗した理由をあえて教えない。「そのIDのサブスクは存在しない」場合と「存在するが他人のものだった」場合を、どちらも `src/server/index.ts` 側で同じ「見つかりません」という結果にまとめている。

もし後者を「これは他人の情報です」と教えてしまうと、少なくともヒントの１つを相手に教えてしまうことになるため。

### サブスクの画面

ブラウザ側で一覧表示・登録フォーム・削除ボタンを表示しているのは `src/client/SubscriptionList.tsx` という React の画面。ログイン中かどうかの切り替え自体は `src/client/App.tsx` が担当していて、ログインしていなければ①の `AuthForm.tsx` を、ログインしていればこちらを表示する。

## ③ ログアウト

ログアウトすると、渡されていた合鍵はサーバー側で無効化される。これも①と同じ Hono の "/api/auth/*" の入り口（つまり `create-auth.ts` の設定に従う Better Auth）が処理し、Neon に保存されている `session` の表からその記録が無効な状態にされる。ブラウザに合鍵の情報が残っていたとしても、それを使ったリクエストはもう受け付けられない。

## ④ 倉庫の鍵（データベース接続情報）の守り方

Neon という倉庫に入るには、専用の「鍵」が必要になる。この鍵は `DATABASE_URL` という接続情報で、
これさえ持っていれば倉庫の中身に直接アクセスできてしまう、非常に強い権限を持つ値。

そのため、この鍵は**プログラムのコードの中に書き込まない**という原則を徹底している。コードは
`src/server/index.ts` などから `c.env.DATABASE_URL` という形で鍵の値を「その場で借りてくる」だけで、
コードそのものには鍵の文字列は一切現れない。

鍵の値は、動かす場所によって別々の安全な保管場所から渡される。

| 動かす場所 | 鍵の保管場所 | 特徴 |
|---|---|---|
| 開発者の手元（ローカル） | `.dev.vars` というファイル | Git の管理対象から外されており、GitHub 上に公開されることはない |
| 本番（Cloudflareの建物） | Cloudflare 側の「シークレット」保管庫（`wrangler secret`で登録） | コードやリポジトリのどこにも文字列として残らない |

この仕組み（Cloudflare Workers の「バインディング」という機能）のおかげで、たとえこのアプリの
ソースコードが誰かの目に触れても、 **そこから倉庫の鍵そのものが漏れることはない**。

これは①〜③で説明してきた「合鍵（ログインのトークン）」とは別物で、合鍵はユーザー1人ぶんの
アクセス権にすぎないのに対し、**この鍵は倉庫そのものを丸ごと開けてしまう**点で、最も守りを固めるべき値になっている。

## まとめ：多重の対策で守っている

1つの仕組みだけに頼らず、複数の層を重ねている。

| 対策 | 何を守るか | 担当ファイル | 使っている技術 |
|---|---|---|---|
| パスワードを読める形で保存しない | パスワードの漏えい | `src/server/auth/create-auth.ts` | Better Auth（変換） / Neon（保管） |
| 決められた場所からのリクエストしか受け付けない | なりすましのログイン | `create-auth.ts`（`trustedOrigins`） | Better Auth |
| 合鍵の有効性を入口で必ず確認する | 未ログインでのアクセス | `src/server/index.ts`（`/api/subscriptions` の関門） | Hono（受付） / Cloudflare（実行場所） |
| 持ち主のいないデータを拒否する | データの矛盾・宙に浮いたデータ | `src/server/db/schema.ts`（表の定義） | Neon（データベース本体の約束事） |
| 自分のデータにしか触れられない | 他人のデータの閲覧・書き換え | `src/server/db/subscriptions.ts` | Drizzle（条件付きの命令組み立て） |
| データベースを扱う窓口を1か所に絞る | 確認漏れの実装が紛れ込むこと | `src/server/db/subscriptions.ts` | Drizzle |
| 倉庫の鍵をコードに書き込まない | 鍵（接続情報）そのものの漏えい | `.dev.vars`（開発時）/ Cloudflareのシークレット保管庫（本番） | Cloudflare Workers（バインディング） |

どれか1つが破られても、他の層が引き続き情報を守る形になっている。
