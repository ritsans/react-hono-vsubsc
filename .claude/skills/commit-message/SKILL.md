コミットメッセージの**案を提示するだけ**のスキル。

## やらないこと

- `git commit` / `git add` / `git reset` など、リポジトリの状態を変えるコマンドは実行しない
- ただし、ユーザーがこの会話で明示的に「コミットして」と指示した場合は、提示した案（または修正後の案）でコミットしてよい

## 手順

1. 変更内容を集める（読み取り専用のコマンドだけを使う）
   ```bash
   git status --short
   git diff --cached --stat
   git diff --cached
   git log -10 --format='%s%n%b---'
   ```
   - ステージ済みの変更があれば、**それだけを対象にする**。未ステージや未追跡のファイルは案に含めず、「ステージされていない変更がある」と一言添える
   - ステージ済みの変更が無ければ、`git diff` と未追跡ファイルを対象にして、その旨を伝える。どちらも無ければ「コミットする変更が無い」と伝えて終わる
2. 会話の文脈から「なぜ」を補う。diff から読める「何を」だけでなく、会話で決めた理由・背景をメッセージに反映する。`docs/progress.md` の最新ログが対象の変更に当たるなら参考にする
3. 変更の関心事が複数混ざっていれば、分割コミットを提案する（どのファイルをどのコミットにするかも示す）
4. 下の形式でメッセージ案を提示する

## 形式

- Conventional Commits（`AGENTS.md` の「コミット規約」に従う）。type は `feat` / `fix` / `docs` / `chore` / `refactor` / `test` / `add` / `db` など。過去のログで使われている type を優先する
- 件名は英語・小文字始まり・命令形・末尾ピリオドなし・72文字以内（例: `feat: add yen conversion for subscriptions`）
- 件名だけで伝わらない変更は、空行を挟んで本文を書く。
- `Co-Authored-By` などのトレーラーは案に含めない

## 出力

コードブロックでメッセージ案を1つ示す。type やまとめ方に迷う余地があれば、別案を1つまで添えて違いを一言で説明する。最後に「コミットする場合は指示してください」とだけ書く。
