# 円換算API 設計

作成日：2026-09-24
ステータス：実装済み（「今月の合計」への集計変更を含む。未コミット・未デプロイ）

## 背景・要件

- 外部サービス：`https://api.frankfurter.dev/v2/` を使用 (過去使われていたv1 は更新停止中。使わない)
- 対象通貨：USD・EUR のみ（JPY は換算不要）
- リアルタイム不要・オンデマンド（ユーザーが「円換算」を押した時だけ呼ぶ）
- 精密さは不要。あくまで参考値
- 円換算は小数点以下四捨五入（2026-09-24 に切り捨てから変更）
- 表示するのは「今月の支払い合計」（下記「集計の対象」）
- 対象通貨によって呼び出すAPIを分ける。必要な通貨のみ取得する（全通貨まとめて取得しない）

## API設計

### `GET /api/exchange-rates?currency=USD`

ログイン必須（既存の `subscriptionsApp` と同じセッションチェックを通す）。

**リクエスト**
- `currency` クエリパラメータ：`USD` または `EUR` のみ許可。それ以外（`JPY` 含む）は `400`

**サーバの処理（上から下へ一本道）**
1. `currency` が `USD` か `EUR` であることを確かめる。それ以外は `400`
2. `https://api.frankfurter.dev/v2/rates?base={currency}&quotes=JPY` を1回だけ呼ぶ
   - 呼び出しは通貨ごとに1本。全通貨まとめて取得しない
3. レスポンスの `rate` が数値であることを確かめて返す
4. Frankfurter が落ちている・想定外の形の場合は `502 { "error": "..." }`エラーを返す。その場合は換算をしない。

**Frankfurter のレスポンス例**

> https://api.frankfurter.dev/v2/rates?base=USD&quotes=JPY

1要素の**配列**で返ってくる（2026-09-24 実測）。
```json
[{ "date": "2026-09-24", "base": "USD", "quote": "JPY", "rate": 157.66 }]
```

**このAPIのレスポンス例 (200)**

Frankfurter の配列から1件目を取り出し、次の形に詰め替えて返す。
```json
{ "date": "2026-09-24", "currency": "USD", "rate": 157.66 }
```
「$1 = 157円 ぐらい」が分かれば良い。

`rate` は「1 USD（または1 EUR）が何円か」。

**キャッシュ**：自前キャッシュはしない。Frankfurter 側が Cloudflare 経由で約20時間キャッシュしていることをヘッダで確認済み（`cache-control: public, max-age=71565`）。推測での最適化はしない。

## 集計の対象（今月の支払い合計）

「円換算」ボタンを押した日の**今月**に実際に支払うサブスクだけを合計する。月額と年額を混ぜて足さない。

- **月払い**：常に全部含める（毎月必ず支払うため。次回支払日は見ない）
- **年払い**：次回支払日の「**月**」が今月と同じときだけ、年額をそのまま含める
  - 「年」は比較しない。年払いは毎年同じ月に請求されるので、支払後に次回支払日を更新し忘れても翌年以降も正しく含まれる
- 「今月」はブラウザのローカル日付で判定する

例：次回支払日が 12月1日 の年払い（6,800円）を、いつボタンを押したか

| 押した日 | 今月の合計に |
|---|---|
| 11月29日 | 含まれない |
| 12月1日 | 6,800円 含まれる |
| 1月2日 | 含まれない |

## フロント側の呼び出し方

「円換算」ボタンを押したときに、**今月の集計対象に実際に含まれている外貨だけ**リクエストする。

- 対象に USD のサブスクが１つでも存在する → USD だけリクエスト（1回）
- 対象に EUR のサブスクが１つでも存在する → EUR も追加でリクエスト
- JPY だけ／対象なし → 通信なし

**換算・丸めのタイミング**：通貨ごとに元の通貨のまま合計 → 円に換算 → **合計後に1回だけ** `Math.round`（四捨五入）。1件ずつ丸めると誤差が積み上がるため。

**エラー時の表示**：「レートを取得できませんでした」と表示するだけ。リトライや前回値の保持はしない（YAGNI）。

## EUR対応（通貨選択肢の追加）

現在 `JPY | USD` の2択になっている箇所すべてに `EUR` を追加する。

| ファイル | 変更内容 |
|---|---|
| `src/server/db/schema.ts` | `currencyEnum` に `"EUR"` を追加。`pnpm db:generate` で `0006`（`ALTER TYPE currency ADD VALUE 'EUR'`）を作成し `db:migrate` で適用 |
| `src/server/db/subscriptions.ts` | `SubscriptionInput.currency` の型に `"EUR"` を追加 |
| `src/server/index.ts` | `parseSubscriptionInput` の通貨チェックに `"EUR"` を追加 |
| `src/client/SubscriptionList.tsx` | 型と `<option>` に EUR を追加 |

⚠ 開発用・本番用で Neon を共有中のため、`0006` 適用はその時点で本番DBにも効く。値の追加のみで既存行に影響はないが、コードのデプロイ前に本番DBだけ EUR を受け付ける状態になる点は把握しておく。

## テスト方針（server project, `app.request()`）

- 未ログインなら `401`
- `currency` が未指定・`JPY`・`GBP` の場合は `400`
- Frankfurter が正常なら `{ date, currency, rate }` を返す（`fetch` をモック）
- Frankfurter がエラーを返す／`rate` が数値でない場合は `502`
- サブスク作成で `currency: "EUR"` が通る

セッションチェックのモックは既存の `index.test.ts` のやり方に合わせる。

## 決定事項の経緯

- レート取得はサーバが中継し、レートだけ返す構成を採用（フロントが集計・丸めを行う）。サーバがサブスク集計まで丸ごとやる案・フロントから直接Frankfurterを叩く案は不採用
- `base=JPY&quotes=USD,EUR` で1回にまとめて逆数を取る方法は不採用。実測で `1/0.00634 = 157.73` となり `base=USD` 直接取得の `157.66` とずれるため
- 対象通貨ごとに呼び出しを分け、必要な通貨のみ取得する（このセクションはユーザー指示により確定）
- 2026-09-24：丸めは四捨五入に統一（当初の要件「切り捨て」と実装の `Math.round` が食い違っていたため）
- 2026-09-24：当初の実装は月額と年額をそのまま足していたため、「今月の支払い合計」に変更。年払いは「月」だけで判定、月払いは常に含める（いずれもユーザー決定）
